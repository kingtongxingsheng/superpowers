# 系统化调试

## 概述

**核心原则：**始终先找根因，再尝试修复。修复症状等于失败。

**违反流程的字面要求，就是违反调试的精神。**

## 铁律

```
没有先调查根因，就不能修复
```

如果还没有完成第一阶段，就不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其要使用：**
- 时间压力下（紧急情况会让猜测变得诱人）
- “先快速修复一下”看起来很明显
- 已经尝试过多次修复
- 之前的修复没有生效
- 还没有完全理解问题

**不要跳过：**
- 问题看起来很简单（简单 bug 也有根因）
- 赶时间（仓促必然返工）
- manager 要求立即修复（系统化调试比反复试错更快）

## 四个阶段

**必须完成每个阶段后才能进入下一个阶段。**

### 第一阶段：根因调查

**在尝试任何修复前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切解决方案
   - 完整阅读 stack trace
   - 记录行号、文件路径和错误码

2. **稳定复现**
   - 能可靠触发吗？
   - 精确步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜

3. **检查最近修改**
   - 哪些变化可能导致此问题？
   - Git diff、最近提交
   - 新依赖、配置变化
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件（CI → build → signing、API → service → database）时：**

   **提出修复前，先加入诊断 instrumentation：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置是否传递
     - 检查每一层的状态

   运行一次，收集证据，确定问题发生在哪里
   然后分析证据，确定失败组件
   然后调查该具体组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第一层：Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第二层：Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第三层：Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第四层：实际 signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：**哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误位于深层调用栈时：**

   阅读本目录的 `root-cause-tracing.md`，了解完整的反向追踪技术。

   **快速版本：**
   - 错误值从哪里产生？
   - 谁用错误值调用了这里？
   - 持续向上追踪，直到找到来源
   - 在来源修复，不要在症状处修复

### 第二阶段：模式分析

**修复前先找到模式：**

1. **查找可工作的示例**
   - 在同一代码库中找到类似的正常代码
   - 与损坏部分相似的内容中，什么是正常工作的？

2. **与参考实现比较**
   - 如果要实现某个模式，完整阅读参考实现
   - 不要略读——逐行阅读
   - 完全理解模式后再应用

3. **识别差异**
   - 正常和损坏部分之间有什么不同？
   - 列出每一项差异，不论多小
   - 不要假设“这不可能有影响”

4. **理解依赖**
   - 需要哪些其他组件？
   - 需要哪些设置、配置和环境？
   - 它依赖哪些假设？

### 第三阶段：假设与测试

**科学方法：**

1. **提出单一假设**
   - 清楚表述：“我认为 X 是根因，因为 Y。”
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做出测试假设所需的最小改动
   - 一次只改变一个变量
   - 不要同时修复多件事

3. **继续前验证**
   - 生效了吗？是 → 第四阶段
   - 没生效？提出新的假设
   - 不要在上面继续叠加修复

4. **不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 请求帮助
   - 继续研究

### 第四阶段：实施

**修复根因，而不是症状：**

1. **创建失败测试用例**
   - 尽可能简单的复现
   - 可以时使用自动化测试
   - 没有框架时使用一次性测试脚本
   - 修复前必须存在
   - 使用 `superpowers-cn:test-driven-development` 技能编写正确的失败测试

2. **实施单一修复**
   - 处理已识别的根因
   - 一次只做一个变化
   - 不要“顺便”改进
   - 不要捆绑重构

3. **验证修复**
   - 现在测试通过了吗？
   - 其他测试没有损坏吗？
   - 问题真的解决了吗？
   - 声称成功前使用 `superpowers-cn:verification-before-completion` 技能

4. **修复无效时**
   - 停止
   - 统计：已经尝试了多少次修复？
   - 如果少于 3 次：回到第一阶段，结合新信息重新分析
   - **如果达到 3 次或更多：停止并质疑架构（见下面第 5 步）**
   - 没有架构讨论，不要尝试第 4 次修复

5. **3 次以上修复失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都会在不同位置暴露新的共享状态/耦合/问题
   - 修复需要“规模巨大的重构”才能实现
   - 每次修复都会在其他地方制造新症状

   **停止并质疑基础：**
   - 这个模式从根本上可靠吗？
   - 我们是否只是“因为惯性而硬撑”？
   - 应该重构架构，还是继续修复症状？

   **再次修复前与 human partner 讨论。**

   这不是假设失败，而是架构错误。

## 红旗——停止并遵循流程

如果发现自己在想：
- “现在先快速修复，之后再调查”
- “先改 X 看看能否解决”
- “一次加几个修改再运行测试”
- “跳过测试，我手动验证”
- “可能是 X，我来修复”
- “我不完全理解，但这可能有效”
- “模式说应该是 X，但我换一种方式适配”
- “主要问题是：[列出未经调查的修复]”
- 在追踪数据流前提出解决方案
- **“再试一次修复”（已经尝试过 2 次时）**
- **每次修复都在不同位置暴露新问题**

**这些想法都意味着：停止，回到第一阶段。**

**如果 3 次以上修复失败：**质疑架构（见第四阶段第 5 步）。

## human partner 表明你做错了的信号

**注意以下引导：**
- “它不是没有发生吗？”——你没有验证就做了假设
- “它会向我们展示……吗？”——你本应收集证据
- “停止猜测。”——你还没理解就提出了修复
- “深入思考。”——质疑基础，而不只是症状
- “我们卡住了吗？”（沮丧）——你的方法不起作用

**看到这些信号时：**停止，回到第一阶段。

## 常见合理化

| 借口 | 事实 |
|--------|---------|
| “问题很简单，不需要流程。” | 简单问题也有根因。流程对简单 bug 很快。 |
| “这是紧急情况，没时间走流程。” | 系统化调试比反复猜测和试错更快。 |
| “先试这个，再调查。” | 第一个修复会形成模式。一开始就正确处理。 |
| “确认修复有效后再写测试。” | 没有测试的修复无法稳定保留。测试优先才能证明它。 |
| “一次修复多个问题更省时间。” | 无法隔离哪个修改有效，还会引入新 bug。 |
| “参考实现太长，我调整模式就好。” | 理解不完整必然产生 bug。完整阅读。 |
| “我看到问题了，来修复。” | 看见症状 ≠ 理解根因。 |
| “再试一次修复。”（失败 2 次后） | 失败 3 次以上说明是架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查修改、收集证据 | 理解是什么以及为什么 |
| **2. 模式** | 查找正常示例、比较 | 识别差异 |
| **3. 假设** | 提出理论、最小化测试 | 确认或提出新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 流程显示“没有根因”时

如果系统化调查表明问题确实来自环境、依赖时序或外部因素：

1. 你已经完成了流程
2. 记录调查过的内容
3. 实施适当处理（重试、超时、错误消息）
4. 增加监控/日志，方便未来调查

**但是：**95% 的“没有根因”其实是调查不完整。

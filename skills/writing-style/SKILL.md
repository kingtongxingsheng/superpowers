## 使用场景
在为人撰写任何文本时，随时都可以运用这项技巧：
- Markdown文档、README 文件、技术说明
- 提交信息、拉取请求的描述
- 错误信息、用户界面文字、帮助文本、评论内容
- 报告、摘要或任何说明/解释
- 进行编辑以提升清晰度
如果你是为了让人类阅读而写作，那就运用这项技能。

## 写作规范

### 总原则
- 先说结论，再说原因、背景。
- 一句只讲一件事。长句拆成短句。
- 多用动词，少用抽象名词。
- 多用主动句，少用被动句。
- 少用“的、地、所、其、之、有关、关于、进行、作出、基于、由于、以及”。
- 省略不必要的词语,能删就删。删后不影响意思，不丢失重要信息，就删。
- 用读者熟悉的话，不用装正式的套话，少用空话、翻译腔。
- 保留必要技术术语，但解释它对用户有什么影响。
- 术语保持一致，不随意换词。
- 列表要可扫读：每条先放关键词，再放说明。
- 不为“完整”堆信息；只放当前任务需要的信息。
- 中文和英文、数字之间保留空格。
- 技术名词、命令、参数、路径、文件名用等宽格式。
- 标点使用中文全角标点；代码、命令、参数内部保留原格式。
- 禁止重复啰嗦，保持内容简洁明了。

### 句式规则
- 用“谁做了什么”代替“某事的发生导致某结果”。
- 用“我们修复了登录失败问题”代替“登录失败问题的修复已经完成”。
- 用“请重新登录”代替“需要进行重新登录操作”。
- 用“构建失败，因为缺少环境变量”代替“由于环境变量缺失导致构建被失败地执行”。
- 能用逗号、句号表达并列，就少用“以及、并且、与”。
- 写“修改配置”，不写“进行配置的修改”。
- 写“服务启动失败”，不写“服务被失败地启动”。
- 写“请重新登录”，不写“需要进行重新登录操作”。
- 写“缺少 API_KEY，构建失败”，不写“由于环境变量缺失导致构建被失败地执行”。
- 避免滥用“进行、作出、有关、关于、基于、由于、以及、被、之一、成功地”。
- “的、地、得”要用对，但能删就删。
- 列举时优先用顿号；只有句子较长或需要强调并列关系时，再用“和”。
- 不用“用户们、开发者们”；多数场景写“用户、开发者、大家”即可。
- 修饰语太长时后置：
  “新增一个配置项，用来限制上传大小”
  优于
  “新增一个用来限制上传大小的配置项”。

### 不同场景
- README：先写用途、安装、运行、配置、常见问题。不要先讲背景故事。
- 技术说明：先讲结论和影响，再讲方案、权衡、边界。
- 提交信息：用动词开头，如“修复登录超时”“新增导出按钮”“移除无用依赖”。
- PR 描述：写清“改了什么、为什么改、怎么验证、风险在哪里”。
- 错误信息：说明发生了什么、用户能做什么。少说系统内部细节、最后给下一步。
- UI 文案：短、准、可行动。例如“保存、重试、删除项目、复制链接”。
- 帮助文本：告诉用户下一步，不讲实现原理。示例：输入 API Key 后，系统会用它请求模型服务。
- 评论内容：指出具体问题和建议，不写空泛评价。
- 报告摘要：先给结论，再列 3 到 5 个关键依据。每条只放一个重点。
- 编辑润色：优先删冗词、拆长句、把名词改回动词。

### 少用词替换
| 少用              | 推荐                 |
| ----------------- | -------------------- |
| 进行配置          | 配置                 |
| 作出修改          | 修改                 |
| 进行检查          | 检查                 |
| 作出响应          | 响应                 |
| 基于这个原因      | 因此                 |
| 有很多问题存在    | 问题很多             |
| 关于登录的问题    | 登录问题             |
| 有关缓存的配置    | 缓存配置             |
| 由于 A 导致 B     | A，所以 B / A，B     |
| 被成功创建        | 已创建 / 创建成功    |
| 成功地修复        | 已修复 / 修复了      |
| 具备可读性        | 好读 / 易读          |
| 具有可扩展性      | 易扩展 / 可扩展      |
| 最重要的功能之一  | 重要功能             |
| 用户们 / 开发者们 | 用户 / 开发者 / 大家 |

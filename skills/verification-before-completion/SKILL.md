# 完成前验证

## 概述

**核心原则：**始终让证据先于断言。

**违反规则的字面要求，就是违反规则的精神。**

## 铁律

```
没有新鲜的验证证据，就不能声称完成
```

如果你没有在当前消息中运行验证命令，就不能声称它通过了。

## 门禁函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令可以证明这个断言？
2. 运行：执行完整命令（新鲜、完整）
3. 阅读：阅读完整输出，检查退出码并统计失败数
4. 验证：输出是否确认了断言？
   - 如果否：根据证据说明实际状态
   - 如果是：带证据说明断言
5. 只有此时：才能做出断言

跳过任何一步 = 撒谎，而不是验证
```

## 常见断言

| 断言 | 必需证据 | 不充分的证据 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 个失败 | 之前的运行、“应该通过” |
| Linter 干净 | Linter 输出：0 个错误 | 部分检查、推断 |
| 构建成功 | 构建命令：退出码 0 | Linter 通过、日志看起来正常 |
| Bug 已修复 | 原始症状测试：通过 | 代码已修改、假设已修复 |
| 回归测试有效 | 已验证红-绿循环 | 测试只通过一次 |
| 代理已完成 | VCS diff 显示修改 | 代理报告“成功” |
| 满足要求 | 逐行清单 | 测试通过 |

## 红旗——停止

- 使用“应该”“大概”“似乎”等词
- 在验证前表达满意（“太好了！”“完美！”“完成！”等）
- 准备提交/推送/创建 PR 却尚未验证
- 相信代理的成功报告
- 依赖部分验证
- 想着“就这一次”
- 疲惫，只想结束工作
- **任何暗示成功、但没有运行验证的措辞**

## 防止合理化

| 借口 | 事实 |
|---------|---------|
| “现在应该可以了。” | 运行验证。 |
| “我有信心。” | 信心 ≠ 证据。 |
| “就这一次。” | 没有例外。 |
| “Linter 通过了。” | Linter ≠ compiler。 |
| “代理说成功了。” | 独立验证。 |
| “我很累。” | 疲惫 ≠ 借口。 |
| “部分检查已经够了。” | 部分检查证明不了任何事。 |
| “换一种说法，规则就不适用了。” | 以精神为准，而不是钻字面空子。 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] “所有测试通过。”
❌ “现在应该通过了。”/“看起来正确。”
```

**回归测试（TDD 红-绿）：**
```
✅ 编写 → 运行（通过）→ 撤销修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ “我已经写了回归测试”（没有红-绿验证）
```

**构建：**
```
✅ [运行构建] [看到：退出码 0] “构建通过。”
❌ “Linter 通过了。”（Linter 不检查编译）
```

**要求：**
```
✅ 重新阅读计划 → 创建清单 → 逐项验证 → 报告缺口或完成
❌ “测试通过，阶段完成。”
```

**代理委派：**
```
✅ 代理报告成功 → 检查 VCS diff → 验证修改 → 报告实际状态
❌ 相信代理报告
```

## 适用时机

**始终在以下操作前使用：**
- 任何形式的成功/完成断言
- 任何满意表达
- 任何关于工作状态的正面陈述
- 提交、创建 PR、完成任务
- 转入下一个任务
- 派遣代理

**规则适用于：**
- 精确短语
- 改写和同义词
- 对成功的暗示
- 任何暗示完成/正确性的沟通

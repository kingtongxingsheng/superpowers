# 技能编写最佳实践

> 学习如何编写有效、易发现且能被 agent 正确使用的技能。

优秀技能应当简洁、结构清晰，并通过真实使用进行测试。本指南说明常见的编写决策。

## 核心原则

### 保持简洁

上下文窗口是公共资源。技能会与 system prompt、对话历史、其他技能元数据和实际请求共同占用上下文。启动时只预加载所有技能的 `name` 和 `description`；只有技能相关时才读取 `SKILL.md`，需要时才读取其他文件，但主文件仍应尽量简洁。

默认假设 agent 已经很聪明。只补充 agent 不知道的内容，并逐段询问：agent 真的需要这个解释吗？可以假设它知道这件事吗？这段文字值得占用 token 吗？

**简洁示例：**

````markdown
## 提取 PDF 文本

使用 pdfplumber：

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

无需解释 PDF 是什么，或详细介绍库的概念。

### 设置合适的自由度

让细节程度匹配任务的脆弱性和可变性：

- **高自由度：** 多种方式都有效、决策依赖上下文、由启发式方法指导。适合代码审查等任务。
- **中自由度：** 存在首选模式、允许有限变化、配置会影响行为。适合带参数的模板或脚本。
- **低自由度：** 操作脆弱、错误代价高、一致性关键、必须按固定顺序执行。适合数据库迁移等操作，明确要求准确运行命令，不要修改参数。

可以把 agent 想象成探索路径的机器人：两侧是悬崖的窄桥需要明确护栏，无遮挡的开阔地则可以给出方向并保留判断空间。

### 使用所有目标模型测试

技能是模型的附加指导，效果取决于底层模型。应测试计划使用的每个模型：Haiku 是否获得足够指导，Sonnet 是否清晰高效，Opus 是否避免过度解释。跨模型使用时，目标是所有模型都能稳定工作。

## 技能结构

`SKILL.md` frontmatter 至少需要：

- `name`：人类可读名称，最多 64 个字符；
- `description`：说明技能做什么以及何时使用的一行描述，最多 1024 个字符。

### 命名约定

建议使用动名词形式，便于引用和讨论，例如 Processing PDFs、Analyzing spreadsheets、Managing databases、Testing code、Writing documentation。也可使用名词短语或动作短语。

避免 `Helper`、`Utils`、`Tools` 等含糊名称，避免 `Documents`、`Data`、`Files` 等过于泛化的名称，也不要在技能集合中混用不一致的命名模式。

### 编写有效 description

description 对技能发现至关重要，应包含关键术语和具体触发场景。使用第三人称，因为它会被注入 system prompt。

有效示例：

```yaml
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
```

避免 `Helps with documents`、`Processes data`、`Does stuff with files` 等模糊描述。

## 渐进式披露

把 `SKILL.md` 当作概览和导航目录，把较大的说明拆到只有需要时才加载的文件中。主文件建议少于 500 行；接近上限时拆分。

典型结构：

```text
pdf/
├── SKILL.md              # 主说明
├── FORMS.md              # 表单指南
├── reference.md          # API 参考
├── examples.md           # 使用示例
└── scripts/
    ├── analyze_form.py
    ├── fill_form.py
    └── validate.py
```

参考文件应由 `SKILL.md` 直接链接。避免多层嵌套引用，因为 agent 可能只预览更深层文件的一部分。超过 100 行的参考文件应在顶部提供目录。

可以按领域组织内容，例如 `reference/finance.md`、`reference/sales.md`、`reference/product.md`，让 agent 只读取与当前请求有关的部分。对于条件性细节，在主文件提供基础用法，并链接高级文件。

## 工作流和反馈循环

### 为复杂任务使用工作流

把复杂操作拆成清晰的顺序步骤。可以提供 agent 能复制并勾选的清单：读取源文件、识别主题、交叉核对声明、创建结构化摘要、验证引用。涉及代码时，步骤应包括分析、建立映射、验证、执行和检查输出。

### 实现反馈循环

常见模式是：运行验证器 → 修复错误 → 重复。验证应尽早发生，失败时明确指出错误位置；只有验证通过后才继续。对于高风险或批量操作，先生成结构化计划文件，验证计划，再执行并验证结果。

## 内容指南

### 避免时效性信息

不要把会过时的规则放在主流程中。当前方法和旧模式分开，旧模式明确标记为历史或弃用。

### 统一术语

在整个技能中选择一个术语并坚持使用，例如始终使用 “API endpoint”“field”“extract”，不要交替使用多个近义词。术语一致能帮助 agent 理解并遵循说明。

### 模板模式

对严格输出格式提供精确模板；对需要适配的场景提供合理默认格式并允许调整。模板应明确标题、必需字段、顺序和可变部分。

### 示例模式

当输出质量依赖示例时，提供输入/输出对。示例要体现期望的风格、详细程度和格式，而不是只重复 description。

### 条件工作流模式

先判断任务类型，再进入对应分支，例如创建新内容时使用创建工作流，编辑已有内容时使用编辑、验证和重新打包工作流。若工作流过大，将对应部分拆为独立文件并明确告知何时读取。

## 评估和迭代

### 先建立评估

在编写大量文档前创建评估，避免记录想象中的需求：

1. 在没有技能时运行代表性任务，记录失败和缺失上下文；
2. 创建至少三个覆盖这些缺口的场景；
3. 测量基线表现；
4. 编写足以解决缺口的最小说明；
5. 运行评估，与基线比较并继续迭代。

评估应包含使用的技能、用户请求、输入文件和预期行为。评估是衡量技能效果的真实来源；若没有内置运行器，可自行创建评估系统。

### 与 agent 迭代

可以让 Agent A 协助编写技能，再由带技能的全新 Agent B 在真实相关任务中测试。观察 B 是否找到正确资料、正确应用规则以及处理异常，并把具体观察结果带回 A。对于已有技能，同样遵循“真实使用 → 观察行为 → 调整结构或措辞 → 重新测试”的循环。

不要只依赖假设；注意 agent 的探索路径、是否错过引用、是否过度依赖某节，以及是否从未访问某个捆绑文件。`name` 和 `description` 是发现阶段的关键。

## 应避免的反模式

- 路径始终使用 `/`，不要使用 Windows 风格的 `\`；
- 不要提供过多方案，应给出默认方案和必要时的替代方案；
- 不要把所有细节堆入主文件；
- 不要用不真实或人为臆造的示例；
- 不要让脚本只把错误推给 agent；
- 不要使用没有解释的 magic number。

## 包含可执行代码的技能

### 解决问题，不要推诿

脚本应处理已知错误条件，给出清晰错误消息或安全替代方案。配置参数应有理由，避免 `TIMEOUT = 47` 之类的 magic number；注释说明值的依据和权衡。

### 提供工具脚本

预制脚本比临时生成代码更可靠、节省 token 和时间，并能保证多次使用的一致性。说明脚本是应执行还是仅作为复杂逻辑参考；多数工具脚本应直接执行。

### 使用视觉分析

输入可以渲染为图像时，让 agent 分析图像，尤其适合表单布局、图表和视觉结构。必要时提供转换脚本。

### 创建可验证的中间产物

对复杂、开放式或破坏性任务，采用“分析 → 生成计划文件 → 验证计划 → 执行 → 验证输出”。验证器应给出具体、可修复的错误，例如指出缺失字段和可用字段。

### 依赖和运行环境

技能运行环境受平台限制：`claude.ai` 可以安装 npm、PyPI 包并从 GitHub 获取内容；Anthropic API 没有网络访问，也不能在运行时安装包。将依赖列入 `SKILL.md`，并确认目标平台提供这些依赖。

技能通过文件系统和 bash 访问文件；启动时加载元数据，正文按需读取，脚本可执行但不必把完整源代码加载进上下文。路径、文件名和目录结构会直接影响发现，文件名应描述内容。

### MCP 工具引用

使用 MCP 时始终使用完整限定名，格式为 `ServerName:tool_name`，例如 `BigQuery:bigquery_schema` 或 `GitHub:create_issue`，避免工具找不到。

### 不要假设工具已安装

明确写出必需依赖和安装方式，或提供无依赖 fallback。不要只说“使用 PDF 库”，却不说明具体包和用法。

## 技能发布前清单

### 核心质量

- [ ] description 具体并包含关键词
- [ ] description 说明触发场景
- [ ] `SKILL.md` 少于 500 行
- [ ] 额外细节已拆分
- [ ] 没有未标记的时效信息
- [ ] 术语一致
- [ ] 示例具体
- [ ] 引用深度只有一层
- [ ] 工作流步骤清晰

### 代码和脚本

- [ ] 脚本解决问题而不是推诿
- [ ] 错误处理明确且有帮助
- [ ] 没有无依据的 magic number
- [ ] 依赖已列出并验证
- [ ] 脚本文档清楚
- [ ] 路径使用正斜杠
- [ ] 关键操作有验证步骤
- [ ] 质量关键任务包含反馈循环

### 测试

- [ ] 至少创建三个评估
- [ ] 使用计划支持的模型测试
- [ ] 使用真实场景测试
- [ ] 已纳入团队反馈（如适用）

发布前应确认技能能被发现、被完整读取，并在真实任务中正确应用。
